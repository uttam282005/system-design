
# Task Management System — LLD Interview Notes

These are the notes I'd keep for **revision before an LLD interview**. The goal is not to memorize code; memorize the **reasoning process and responsibilities**.

---

## 1. Problem Scope

Build a task management system supporting:

* Create task
* Delete task
* Assign task to user
* Change task status
* Change priority
* Add comments
* Add subtasks
* List/filter tasks

### Status

```cpp
enum class TaskStatus {
    TODO,
    IN_PROGRESS,
    DONE,
    CANCELLED
};
```

### Priority

```cpp
enum class Priority {
    LOW,
    MEDIUM,
    HIGH
};
```

# 2. First Question: What are the entities?

Don't immediately create classes.

Identify the nouns:

```text
User
Task
Comment
```

Potential future entities:

```text
Project
Label
Notification
Dependency
```

**Only introduce them if requirements need them.**

For a 45-minute interview, avoid unnecessary entities.

---

# 3. Relationships

```text
User
  |
  | assigned to
  ↓
Task
 ├── Comments
 └── Subtasks
```

Think carefully about cardinality:

```text
1 User → many Tasks
1 Task → many Comments
1 Task → many Subtasks
```

# 4. Most Important Class: Task

Task owns **its own state and invariants**.

```cpp
class Task {
private:
    int id;
    string title;
    string description;

    TaskStatus status;
    Priority priority;

    optional<int> assigneeId;

public:
    void assignTo(int userId);
    void changeStatus(TaskStatus status);
    void setPriority(Priority priority);

    void addComment(Comment comment);
    void addSubtask(shared_ptr<Task> task);
};
```

### Key principle

> **An object should control changes to its own state.**

Don't expose:

```cpp
task.setStatus(DONE);
```

if status transitions have business rules.

Prefer:

```cpp
task.changeStatus(DONE);
```

because `Task` can validate the transition.

---

# 5. Entity vs Service

This is one of the most important concepts.

### Task

Responsible for:

```text
"Is this state change valid?"
```

Example:

```text
TODO → IN_PROGRESS ✓
IN_PROGRESS → DONE ✓
DONE → TODO ✗
```

### TaskService

Responsible for:

```text
"How do I execute this use case?"
```

Example:

```text
assignTask(taskId, userId)

1. Find task
2. Find user
3. Validate user
4. Modify task
5. Save task
```

So:

```text
Task
 ↓
business rules / invariants

TaskService
 ↓
use-case orchestration
```

---

# 6. Don't create a God class

Avoid:

```cpp
class TaskManager {
    createUser();
    createTask();
    sendEmail();
    saveDatabase();
    search();
    authenticate();
    ...
};
```

This violates separation of responsibilities.

Prefer:

```text
TaskService
UserService
NotificationService
AuthorizationService
```

For the 45-minute version, you only need:

```text
TaskService
```

plus repositories.

---

# 7. TaskService

Recommended interface:

```cpp
class TaskService {
private:
    ITaskRepository& taskRepository;
    IUserRepository& userRepository;

public:
    TaskService(
        ITaskRepository& taskRepository,
        IUserRepository& userRepository
    );

    int createTask(
        const string& title,
        const string& description,
        Priority priority
    );

    void assignTask(
        int taskId,
        int userId
    );

    void changeStatus(
        int taskId,
        TaskStatus newStatus
    );

    void deleteTask(
        int taskId
    );
};
```

### Why references?

Because dependencies are injected:

```text
TaskService
    |
    +---- ITaskRepository
    |
    +---- IUserRepository
```

This is **Dependency Injection**.

---

# 8. Why createTask doesn't take taskId

Don't do:

```cpp
createTask(taskId, ...)
```

The ID should be generated by the persistence layer/service.

```cpp
int taskId = createTask(...);
```

The caller receives the generated ID.

---

# 9. Why assignment is separate from creation

Prefer:

```cpp
createTask(...)
assignTask(taskId, userId)
```

instead of:

```cpp
createTask(
    title,
    description,
    priority,
    assigneeId
);
```

Reason:

**Creating and assigning are separate use cases.**

It also avoids making `createTask()` grow as requirements change.

---

# 10. Repository Pattern

The service shouldn't know whether tasks are stored in:

```text
PostgreSQL
MongoDB
Memory
```

Define:

```cpp
class ITaskRepository {
public:
    virtual ~ITaskRepository() = default;

    virtual shared_ptr<Task>
    findById(int id) = 0;

    virtual void save(
        shared_ptr<Task> task
    ) = 0;

    virtual void remove(int id) = 0;
};
```

Similarly:

```cpp
class IUserRepository {
public:
    virtual ~IUserRepository() = default;

    virtual optional<User>
    findById(int id) = 0;
};
```

---

# 11. Why Repository?

Without repository:

```text
TaskService
    ↓
SQL
```

Now business logic is coupled to the database.

With repository:

```text
TaskService
    ↓
ITaskRepository
    ↓
PostgresTaskRepository
```

Benefits:

* Separation of concerns
* Easy testing
* Database can change
* Business logic doesn't depend on SQL

---

# 12. In-memory implementation for interview

Don't waste interview time implementing PostgreSQL.

Use:

```cpp
class InMemoryTaskRepository
    : public ITaskRepository {

private:
    unordered_map<int, shared_ptr<Task>> tasks;

public:
    ...
};
```

Then tell the interviewer:

> "For the interview I'll use an in-memory repository. In production this interface can have a PostgreSQL implementation."

That's enough.

---

# 13. Dependency Injection

Bad:

```cpp
TaskService::TaskService() {
    taskRepository =
        PostgresTaskRepository();
}
```

Good:

```cpp
TaskService(
    ITaskRepository& taskRepository,
    IUserRepository& userRepository
);
```

Now testing is easy:

```text
TaskService
     |
     +---- MockTaskRepository
     +---- MockUserRepository
```

---

# 14. `assignTask()` reasoning

```cpp
void assignTask(
    int taskId,
    int userId
);
```

Flow:

```text
assignTask()
     |
     ├── taskRepository.findById()
     |
     ├── userRepository.findById()
     |
     ├── validate
     |
     ├── task.assignTo(userId)
     |
     └── taskRepository.save()
```

Important:

**TaskService checks whether the user exists.**

**Task controls its own assignment state.**

---

# 15. `changeStatus()` reasoning

```cpp
void changeStatus(
    int taskId,
    TaskStatus newStatus
);
```

Flow:

```text
TaskService
     |
     ↓
find Task
     |
     ↓
task.changeStatus(newStatus)
     |
     ↓
repository.save()
```

Don't do this:

```cpp
if (newStatus == DONE) {
    ...
}
```

inside `TaskService`.

The status transition rules belong to `Task`.

---

# 16. Encapsulation

Avoid exposing mutable fields:

```cpp
task.status = DONE;       // BAD
task.priority = HIGH;    // BAD
task.assigneeId = 10;    // BAD
```

Instead:

```cpp
task.changeStatus(DONE);
task.setPriority(HIGH);
task.assignTo(10);
```

This lets the class enforce invariants.

---

# 17. Subtasks

Model as:

```text
Task
 ├── Subtask
 ├── Subtask
 └── Subtask
```

Can use:

```cpp
vector<shared_ptr<Task>> subtasks;
```

But remember:

### Prevent cycles

Invalid:

```text
A
 ↓
B
 ↓
C
 ↓
A
```

If interviewer asks, mention DFS/BFS or ancestor checking.

Don't spend 10 minutes implementing it unless requested.

---

# 18. Comments

Simple:

```cpp
class Comment {
private:
    int id;
    int authorId;
    string content;
};
```

Task can expose:

```cpp
void addComment(Comment comment);
```

For a real large-scale system, comments shouldn't necessarily be loaded every time a Task is loaded.

You can mention:

> "In production, comments would have their own repository/table and be fetched separately."

---

# 19. Filtering

Don't create:

```cpp
getTasks(
    status,
    priority,
    assignee,
    label,
    dueDate,
    ...
);
```

Use:

```cpp
struct TaskFilter {
    optional<TaskStatus> status;
    optional<Priority> priority;
    optional<int> assigneeId;
};
```

Then:

```cpp
vector<Task> getTasks(
    const TaskFilter& filter
);
```

### Why?

Adding a new filter doesn't require changing the method signature.

# 20. Error handling

Have clear domain errors:

```text
TaskNotFound
UserNotFound
InvalidStatusTransition
Unauthorized
ConcurrentModification
```

Map conceptually:

```text
TaskNotFound
    → 404

InvalidStatusTransition
    → 400 / 409

Unauthorized
    → 403

ConcurrentModification
    → 409
```

For the LLD, exceptions are sufficient.

# 21. Important invariants

Before coding, explicitly identify these.

### Task

```text
- ID must be unique
- title shouldn't be empty
- status must be valid
- priority must be valid
```

### Assignment

```text
- task must exist
- user must exist
```

### Status

```text
- only valid transitions
```

### Subtasks

```text
- no circular hierarchy
```

### Deletion

Decide:

```text
What happens to subtasks?
What happens to comments?
What happens to assignments?
```

Don't leave ambiguous behavior if interviewer asks.

# 22. Concurrency — production discussion

This is one of the strongest points to mention at the end.

Suppose:

```text
Task version = 5
```

Two users read it.

```text
User A → version 5
User B → version 5
```

A updates:

```text
version = 6
```

B tries to update version 5.

Use optimistic locking:

```sql
UPDATE tasks
SET status = ?,
    version = version + 1
WHERE id = ?
AND version = ?;
```

If affected rows = `0`:

```text
ConcurrentModification
```

### Don't use a global mutex.

It doesn't scale across multiple server instances.

# 24. Notifications

Don't do:

```cpp
assignTask() {
    saveTask();
    sendEmail();
}
```

Why?

If email service is down:

```text
Task assignment
    ↓
Database succeeds
    ↓
Email fails
```

Should assignment fail?

**No.**

Instead:

```text
TaskService
    ↓
TaskAssignedEvent
    ↓
Event Bus
    ↓
NotificationService
```

For production reliability:

```text
Transactional Outbox
```

---

# 25. Transactional Outbox

Important production concept.

Inside one DB transaction:

```text
UPDATE task
INSERT event into outbox
COMMIT
```

Then:

```text
Outbox
   ↓
Event Publisher
   ↓
Kafka / Queue
   ↓
Notification
```

This prevents:

```text
DB success
+
event lost
```

from leaving the system inconsistent.

# 30. Golden responsibility table

| Component                | Responsibility                   |
| ------------------------ | -------------------------------- |
| `User`                   | User data                        |
| `Task`                   | Task state + business invariants |
| `Comment`                | Comment data                     |
| `TaskService`            | Use-case orchestration           |
| `ITaskRepository`        | Task persistence abstraction     |
| `IUserRepository`        | User persistence abstraction     |
| `InMemoryTaskRepository` | Interview/testing persistence    |
| `PostgresTaskRepository` | Production persistence           |
| `TaskFilter`             | Search/filter criteria           |

This table is worth memorizing.

# 31. The most important interview principles

### 1. Encapsulation

```text
Don't expose mutable state.
```

### 2. Single Responsibility

```text
Task ≠ database
TaskService ≠ Task
Repository ≠ business logic
```

### 3. Dependency Inversion

```text
Service → Interface
not
Service → PostgreSQL
```

### 4. Composition over inheritance

Don't create:

```text
Task
 ├── HighPriorityTask
 ├── LowPriorityTask
 ├── AssignedTask
 └── CompletedTask
```

Status and priority are **data/state**, not subclasses.

### 5. Program to interfaces

```cpp
ITaskRepository&
```

rather than:

```cpp
PostgresTaskRepository&
```

### 6. Don't overengineer

A simple correct design beats a complicated "enterprise" design.

# 32. Most important questions to ask interviewer

At the beginning, ask **3–5**, not 20.

1. **Who can create/update/delete tasks?**
2. **Can a task have multiple assignees?**
3. **What status transitions are allowed?**
4. **Do we need projects/workspaces?**
5. **Do we need persistence, or can I use in-memory storage for the LLD?**

Then proceed with reasonable assumptions.

# 33. Your mental model

When you see any LLD problem, think:

```text
                REQUIREMENTS
                     ↓
                 ENTITIES
                     ↓
             RESPONSIBILITIES
                     ↓
                INVARIANTS
                     ↓
             CLASS INTERFACES
                     ↓
              COLLABORATION
                     ↓
             DESIGN PATTERNS
                     ↓
         CONCURRENCY / FAILURE
                     ↓
                 SCALE
```

**Do not start with "Which design pattern should I use?"**

Start with:

> **What objects exist, what state do they own, what rules must they protect, and who coordinates operations involving multiple objects?**

That mindset will transfer directly to **Parking Lot, Splitwise, Tic-Tac-Toe, Chess, Elevator, Library Management, Ride Sharing, ATM, and many other LLD interview problems.**
